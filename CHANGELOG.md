# Changelog

All notable changes to Agent Rishi are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [semantic versioning](https://semver.org/).

## [Unreleased]

The notes for the next release are in [`changes/`](changes/README.md), one file per change. The release moves them into a version section here.

## [0.7.10] - 2026-11-25

### Changed

- **Each desk on the Floor shows what its agent is doing.** Every desk where an agent works (prep, build, review and the PM's) now has a laptop, and an occupied desk gets a prop for its step: a glass jar with a red bug and a magnifier while reproducing a bug, the whiteboard and sticky notes while analyzing a feature, a toolbox at the bench (with a wrench for a bug fix or a blueprint roll for a feature) and a clipboard with a red pen while reviewing. Empty desks keep only their laptop, and the props change as soon as an agent moves on to its next step.

### Fixed

- **OpenCode uses the project's own config.** A provider defined in a project's `opencode.json`, `opencode.jsonc` or `.opencode/opencode.json` that git doesn't track (such as a custom router) now shows up in the model picker for that project, in New session, the session composer and the project's default model, and its sessions can run it instead of failing with "Model unavailable". Agent Rishi lists OpenCode's models per project and gives each session the project's config from its main checkout. Your inline config and Agent Rishi's own settings stay on top, so Agent Rishi's permission rules, its plugin and its MCP server always win, and a project config never brings in plugins or permission rules. A config file that isn't valid JSON is left out with a warning in the model picker and in the session. Only the config file is read from `.opencode/`: its agents, commands and plugins are not.
- **OpenCode's model list is waited for, not guessed at.** OpenCode 2.4.x loads its providers and models a second or more after its server prints its start-up URL, so Agent Rishi's model probe could read an empty list and leave the picker with only **Default** ("OpenCode listed no models"), hiding your configured models and their reasoning-effort levels. The probe now polls OpenCode's provider and model lists until they settle, within its existing 20-second budget. The utility model's cheap-model lookup waits the same way, so session titles, follow-up suggestions and summaries keep using a cheap model instead of silently falling back to the default one.
- **Full no longer asks for ordinary commands in a worktree.** Commands that name where the shell is (`cd "$(pwd)/apps/web"`, `Set-Location (Get-Location)`) run without asking again at Full and Auto, and no level asks any more for a name of three or more dots in the worktree (`go test ./...`, a `'...'` in a one-liner), which counted as Agent Rishi's own home because session worktrees live there.
- **Desktop crash recovery.** Agent Rishi retries failed window loads and reloads the window after a renderer crash. If recovery fails, use **Help > Retry Loading Agent Rishi**. **Help > Export Diagnostics** saves a JSON report with recent process exits and quit reasons. The web app offers a reload button after an unexpected error.

### Security

- **Paths built from where the shell is resolve to that folder.** Writing beside the worktree that way (`rm -rf "$(pwd)/../x"`, `"$PWD../x"`) now asks, and so does a `cd` to the folder `pwd`, `Get-Location` or `git rev-parse --show-toplevel` prints once the command line redefines them or changes `PATH`.
- **Windows device paths and empty PowerShell values in a path now ask.** `\\?\C:\…`, `\\.\C:\…` and `\??\C:\…` name the same file as `C:\…`, so Agent Rishi's own home and credentials ask at every level in those forms too. A path that starts with or holds `$null`, `$true`, `$false` or `$_`, which a shell may expand to nothing, asks at Auto and Full. Alone (`> $null`, `Remove-Item $_`), they still run freely.

## [0.7.9] - 2026-11-23

### Security

- **Files read through an interpreter ask like a direct read.** A path in a `python -c`, `node -e`, `ruby -e`, `perl -e` or `php -r` one-liner, in a script written out on an interpreter's input, or handed to PowerShell's `System.IO` types gets the verdict reading that file directly gets: Agent Rishi's own home and credentials ask at every level. Commands that Perl, Ruby and PHP run in backticks, `qx`, `%x` or `shell_exec` are classified too.
- **More ways of running a command are classified.** Delete and copy tools, shells and interpreters a package manager runs by name (`pnpm rimraf`, `yarn run`, `bun run`), and the command run by `wsl`, `conda run`, `mise exec`, `hatch run`, `pipenv run`, `direnv exec`, `dotenv`, `doppler run`, `cross-env`, `fakeroot`, `unshare`, `runuser`, `gosu`, `script -c`, `tmux new`, `screen`, `parallel`, `at` and `batch`. A new crontab asks at Auto and Full.

## [0.7.8] - 2026-11-23

### Added

- **Archive a project from the sidebar.** A project's menu (right-click it, or the **⋯** button) has **Archive project**: after a confirmation the project leaves the list, its automations and factory stop, and the worktrees of its sessions are cleaned up (any with uncommitted changes are kept). Your folder isn't touched, and adding the same folder again brings the project back. A project can't be archived while one of its sessions is working or waiting to start (created, queued, starting, running or waiting); the dialog says how many, and the server refuses the archive too.
- **Hold an issue out of the factory loop.** An issue labelled `factory:hold` is never taken in or started by the software or dark factory: an item of it still waiting in the queue is parked, and work already in progress carries on. Removing the label releases it on the next check. The project manager holds and releases issues with `factory_hold_issue` and `factory_release_issue`, each with an optional reason that is recorded and posted on the issue. The Factory view lists held issues under Intake as "Held" with the reason.
- **A project manager's stop isn't a failure.** When the project manager stops a factory builder or reviewer with a reason (held, superseded, waiting on another pull request), the item is recorded as stopped by the PM with that reason and never counts towards the pause after failures in a row. Failures by the builder, CI or the review still count, and Retry runs the item again.
- **The orchestrator and project managers switch provider when theirs runs out.** When their provider hits its usage limit mid-turn, Agent Rishi moves them to another provider that is installed and signed in, sends your message again, and says so in their chat and the inbox: "Switched from A to B: A hit its usage limit (until 14:30)". Notes, wake-ups, inbox items and queued messages carry over. Once the limit has reset, their next turn moves back to the provider you chose. If no other provider is ready, nothing is switched and the chat says why. Turn it off with **Switch provider automatically when a limit is hit** in **Settings → Providers → Defaults per role**.
- **Start fresh for the orchestrator and project managers.** Their chat is one long conversation, so after a few days of triage and wake-ups it gets hard to read and carries stale context. **Start fresh…** in the chat's ⋯ menu archives the current conversation and starts a new, empty one on the provider and model chosen in **Settings → Providers → Defaults per role**. Project notes, scheduled wake-ups, open inbox items and the work the PM follows carry over; nothing is deleted. It asks first, and waits while a turn is running or a question or approval is open. The earlier conversation stays readable: a PM's is listed with the project's archived sessions, and the toast links to it. It can't be continued, so it never comes back as a second PM.
- **Token saver.** Settings → General → Token saver adds a short note to each session's system prompt that asks for terse answers, the least code and narrow searches, at Lite, Full or Ultra (off by default). Exact technical terms and the words not, never, no and only are kept, and security warnings, irreversible steps and text that leaves the session stay in full sentences. Each role can have its own default, and a project can override it in its settings. It never relaxes Agent Rishi's own rules for a role, permissions or security. Sessions on providers whose system prompt holds for the whole conversation (Claude Code and Codex) get it, whoever started them: you, project managers, the orchestrator, the factory or automations. It applies to sessions started or resumed after a change. (#602)
- **Apply a project's permissions to its open sessions.** A project's permission level is what its new sessions start with, so its Settings tab lists the open sessions that keep another level (#568). That list now has **Apply to open sessions**, which moves each of them to the project's level, as its own Permissions picker would, from the agent's next tool call (Codex: its next turn). When that raises any session's level, such as Auto to Full, Agent Rishi asks first and names the sessions it raises; lowering doesn't ask. A session it couldn't change stays listed with the reason. It's a button for you only: no agent, PM or orchestrator tool can do it (#622).
- **HTTPS through Tailscale Serve.** `agent-rishi network origin add https://<machine>.<tailnet>.ts.net:8445` trusts a reverse proxy on the same computer, so a phone gets notifications, dictation and Add to Home Screen over HTTPS. Requests through it always need the password sign-in, never the install token. `agent-rishi network on --loopback-only` (also in Settings › Network access) keeps Agent Rishi on 127.0.0.1 so the proxy is the only way in. See docs/remote-access.md.

### Changed

- **A PM sees which providers it can start a session on.** The `provider` parameter of the PM's `start_session` tool was a free-form id with nothing to choose from, so a PM found the valid ones by starting sessions and reading the failures. Its description now lists the providers that are loaded and whether each is ready, with the reason and the fix when one isn't (for example `gemini` (Gemini CLI): not installed, fix: `npm install -g @google/gemini-cli`). The orchestrator's `create_project` and `update_project` list them the same way for `defaultProvider`. `start_session` still refuses a provider id that isn't loaded, and the refusal now names the loaded ones.
- **Claude Code 2.1.290 or newer is now the minimum.** Claude's current models refuse older versions ("does not support this model; version 2.1.290 or newer is required"), so setup now flags an older `claude` and offers `claude update`. Agent Rishi's Claude support moves to Claude Agent SDK 0.3.330, which Agent Rishi installs on its own the next time a Claude session starts.

### Fixed

- **Attached images with a special character in their name show again.** An image or shared file whose name held a character outside Latin-1, or a control character other than a tab or a line break, showed as a broken image in the chat, the queue and the image viewer, and couldn't be downloaded, although the agent received it. That covers every macOS screenshot (its name has a narrow no-break space before "AM"/"PM") and names with CJK characters or emoji, on the computer itself and over network access alike; plain names and names with Western European accents were not affected. The server now sends such a name in a form every browser accepts, and downloads keep the full name (#68).
- **A factory pull request is no longer thrown away because its integrator's provider refused to start it.** When the integrator taking over a PR couldn't open (its provider signed out, a CLI too old) while the PR was in verification, it stayed in charge. Each conflict tick then sent it a bare "rebase" request on the same provider. After three of those the work was rebuilt from the default branch and the PR was closed. Now the refused integrator is let go and archived, and its provider is backed off once. In the same tick a fresh integrator, with its full brief, takes over on a provider that can take work. A refused start no longer counts as a request to rebase. An integrator the runner was too busy to answer is waited for a few minutes before it is replaced.
- **A CI-kick request no longer goes to a pull request that was merged or closed in the meantime.** Like rebase requests, it now checks the PR again right before it is sent.
- **A provider you signed in to is no longer held off factory work because of an older refusal.** The factory no longer backs a provider off for an integrator refusal that happened before you signed in or pressed Check now or Retry, or that it already acted on.
- **The agent CLIs and the GitHub CLI are found in the package managers' global folders.** On macOS and Linux, Claude Code, Codex, OpenCode, Gemini CLI and `gh` installed with Bun, pnpm, Volta or npm's own prefix, or in `~/.local/bin` or Homebrew, are found even when those folders are not on Agent Rishi's PATH.
- **Settings > GitHub no longer says the GitHub CLI is not installed while the setup checklist says it is signed in.** The GitHub token was read with whatever `gh` was on the server's PATH, which an app started from the Dock doesn't have, while the checklist also looked in Homebrew's folder. Both now look tools up the same way (PATH, then the tool's known install locations), and so do the server's other `gh` and `git` calls.
- **The macOS desktop app finds tools set up in Terminal.** Launching Agent Rishi from the Dock or Finder picks up Homebrew and Node version manager paths for provider checks and new embedded terminals.
- **Settings > Providers shows each provider's real state.** Every provider the runner loaded was marked Ready, even one that isn't installed or signed in, so it could disagree with the setup checklist. The badge now follows the same checks as the checklist and the model picker: Ready, Not installed, Installed but broken, Not signed in or Too old, with the reason underneath.
- **Cursor's browser login no longer opens again and again on its own.** Background checks (start-up, re-checks, the factory's availability checks) asked the Cursor CLI to sign in over ACP whenever `agent status` said signed in; when the stored login could not actually be used, the CLI opened its browser login each time, and the check stopped it before the login could finish. Checks now never start a login. A login that `agent status` reports but Cursor can't use shows as "needs you to sign in again" with the `agent login` command, and a Cursor session fails with that message instead of opening the browser.
- **`pnpm desktop:build` works on macOS again.** The host-only build pointed electron-builder at the folder of the Electron executable, which on macOS is `Electron.app/Contents/MacOS` rather than the `dist` folder, so packaging stopped with "corrupted Electron dist". It now uses the electron package's `dist` folder on every platform.
- **An old `claude` or `codex` left on PATH no longer hides the current one.** With an outdated copy in `/usr/local/bin` (a leftover npm global install) and a current one in `~/.local/bin`, Agent Rishi took the first copy that ran, so setup showed "Could not read the Claude login state" or "Not signed in to Codex" for a CLI that was signed in. It now keeps looking when a copy is older than the provider's minimum version and uses the first supported one, for the setup checks and for sessions alike, from a runner's first session and model list on (Gemini CLI and OpenCode too). When only an old copy exists, setup says so and names the file ("Claude Code 2.0.8 is older than 2.1.250; update it") instead of offering Sign in, and no longer asks that copy for its login state, which an old `claude` answered with a model call (#561).
- **A project's Permissions say which sessions they don't reach.** A project's permission level is what its new sessions start with, so changing it left running sessions asking as before, with nothing saying why (#568). The project's Settings tab now names the open sessions that keep another level, with links, and says where to change a session's own (its Permissions picker, which applies while it runs). The orchestrator's `update_project` says the same in its result. The docs explain where a session's level comes from, that Supervised asks about every command (reads included), and that the project's autonomy mode doesn't change which actions ask.
- **The orchestrator and project managers can be moved to another provider.** Their provider came from **Settings → Providers → Defaults per role** only when they were first started, so changing it later did nothing, and someone without the default provider (Claude Code not signed in, for example) had no way to use them: every turn failed and the model picker showed the other providers greyed out with "Start a new session to switch providers". Choosing another provider in that setting now retires the current orchestrator or PM conversation, and your next message starts a fresh one on the new provider. Messages still waiting for the old provider (yours, and the orchestrator's tasks and questions for a PM) move to the new conversation, which then starts right away; a conversation with a turn running is left to finish first. Only a change of that setting moves them: a project's own **Default agent** doesn't, and a setting that already named another provider before this version takes effect when you next change it. The picker in their chat says so on the greyed-out providers and has a **Change provider** link to the setting.
- **The factory's `tests` check no longer fails pull requests whose tests are named by another convention.** It said "Code changed but no test files were added or updated" when the changed tests weren't `x.test.*` or `x.spec.*` in JavaScript or TypeScript, `x_test.go`, `x_test.py`, `test_x.py` or in a `test/`, `tests/`, `__tests__/`, `spec/` or `e2e/` folder, and a pull request that failed that way after its revise rounds counted towards the pause after failures in a row. It now also knows .NET test projects (`App.Tests/`, `App.UnitTests/`), test classes (`OrderServiceTest.java`, `OrderTests.cs`, `OrderSpec.scala`), `x_test.rs`, `x_spec.rb`, `x-test.js`, `test_x.sh`, `X.Tests.ps1`, `x.cy.ts`, `x.e2e-spec.ts`, `.test.` and `.spec.` files in other languages, Django's `tests.py`, `conftest.py`, `__snapshots__/` and folders such as `integration-tests/`. As before, a test file is told from its path alone, so it counts whether the pull request added, modified, renamed or removed it.
- **OpenCode custom models fail with a reason you can act on, and a bare model id no longer runs the wrong model.** A model id without its provider (`Worker` instead of `9router/Worker`) silently ran OpenCode's default model; the session now says the id needs the `<providerID>/<modelID>` form that `opencode run -m` takes. "Model unavailable" no longer counts as a passing failure that Agent Rishi retries, and it now explains the usual cause: OpenCode lists models per folder and each session runs in its own worktree, so a provider defined in a project `opencode.json` that git doesn't track isn't there. Set it in your global OpenCode config or commit the file. A custom model OpenCode doesn't list is also sent without an effort level, because OpenCode fails the turn on a level the model doesn't offer.
- **A runner left over from an earlier start no longer keeps working beside the new one.** After the app was quit and reopened, a runner that had stopped answering could keep running for hours: it started agent turns in the same worktrees as the new runner's sessions and held Codex threads, so resuming them failed with "Codex thread … is still open in another process". A new runner now stops a runner that holds the lock but doesn't answer, a runner replaced by another shuts itself down with its agents within seconds, and a runner always exits on SIGTERM, even when an agent never finishes closing.
- **Codex commands run from a subfolder no longer ask for paths inside the worktree.** A command Codex ran from `<worktree>/frontend` with a relative path such as `> ../proof.log` was judged as if it ran from the worktree root, so the path pointed one level above the worktree and asked at every level, Full included ("Writes Agent Rishi's own home" when the worktree sits in Agent Rishi's home). Relative paths in a Codex command now resolve from the folder it runs in, as the shell resolves them. A path that still lands outside the worktree asks as before, and a relative path from a working folder outside the worktree now asks (see Security).
- **A project's Automations list shows that project's own last run.** An automation for all projects showed the newest run from any project, so a project that never ran it could show another project's outcome and time, and a project that did could disagree with its own Runs tab. Each project now sees its own newest run, or none when it hasn't run there; the list of every project still shows the newest run anywhere.
- **Run now and Save and run now tell you when the run failed to start.** When an automation's session or PM message couldn't start, the run was recorded as failed but the app still said "Run started". Both now show "Run failed" with the run's error. Save and run now still saves the automation and opens it, and the failed run stays in its history.
- **Antivirus no longer flags Agent Rishi as malware on Windows.** To find processes an agent left running in its worktree, the runner compiled C# code at runtime with PowerShell's `Add-Type` and read other processes' memory to learn their working folders. Antivirus heuristics flag that pattern as malware (for example `Gen:Variant:MSILHeracles`), blocked it, and the cleanup broke with it. Agent Rishi now never compiles code at runtime and never reads another process's memory. On Windows it finds leftovers by their executable and command line, as before, and, when a session stops, by the process tree: what was still running under the agent when it exited. A process that had already left the tree before the stop (started in the background from a shell that exited earlier) and doesn't name the worktree on its command line may now be missed. macOS and Linux are unchanged.
- **OpenCode sessions get their `/` commands and skills.** With OpenCode as the provider, typing `/` showed nothing, and `/review` or `/my-skill` went to the model as plain text. The `/` menu now lists your OpenCode custom commands (`.opencode/commands/`, `~/.config/opencode/commands/` and the commands in your OpenCode config, nested ones as `team/review`) and your skills (`~/.config/opencode/skills`, `~/.agents/skills`, `~/.claude/skills` and the project's `.opencode/skills`, `.agents/skills` and `.claude/skills`), already in the New session draft. Picking a command runs it in OpenCode, so its template expands with the rest of the line as arguments, and picking a skill loads it with your message. A command OpenCode can't run ends the turn with its reason instead of hanging. Any other text starting with `/` is still sent as typed.
- **A runner replaced by a newer one no longer touches what is now the new runner's.** It used to keep saving the event journal while it shut down, when a server was still connected to it or a save was already due, and it let its sessions finish closing and write checkpoints in worktrees the new runner may be using. It now stops writing at once, closes its connections and ends its agents straight away. A runner that is closing also writes nothing more to the journal once another runner has taken over. On Windows, stopping a runner that stopped answering no longer reaches processes that only had a parent with a reused process id.
- **A PM's session without a named provider starts only on one that is ready.** When the PM's `start_session` named no provider, it fell back to the project's default or the Settings default even when that provider wasn't installed or signed in, and the session then failed to start. It now takes the project's default, else the Settings default for agents (on `auto`, the first ready provider), only when the provider is loaded and ready; when none is, the call is refused with the loaded providers, the state of each and its fix, so the PM can name one that works.
- **The orchestrator can no longer set a project's default provider to one that doesn't exist.** `create_project` and `update_project` stored any provider id as the project's default. They now refuse an id the runner hasn't loaded and name the loaded providers.
- **An archived project's sessions are read-only.** A message to a session of an archived project still ran a turn. Archiving now makes the project's sessions read-only: their transcripts stay open to read, but the server refuses new input to them from anyone (your messages, the PM's and orchestrator's, automations, the factory, notices and wake-ups) with "This project is archived", and the session's composer says the project is archived instead of offering to send. Adding the project's folder again restores it.
- **Files you attach to a message now reach the agent, the orchestrator and PMs included.** A PDF, a spreadsheet or any other file that isn't an image used to arrive as its bare name with no file behind it, so the orchestrator said it couldn't see it and other agents found it only when a file of that name happened to sit in their worktree (#611). The composer now sends the file itself (up to 20 MB, like images; a larger one is named in a notice and left out), Agent Rishi keeps it in the session's own artifacts folder under its own name (made safe for every file system; names in any script, such as `отчёт.pdf` or `報告.docx`, stay as they are), and the agent gets that file's full path, which it may read without asking. Agent Rishi writes only the bytes it received and never opens a path the browser names.
- **CLI updates.** The installer keeps inherited npm registry, proxy, certificate authority and user config settings, and filters out other inherited npm configuration variables, including client certificates and auth tokens, during side-by-side updates.

### Security

- **A PowerShell assignment no longer hides a command from the Auto checks.** `$r = Remove-Item C:\… -Recurse`, `$x = Set-ItemProperty HKCU:\…\Run …`, `$e = Get-ChildItem env:; $e`, `$null = irm … | iex` and `$x = git push --force` ran without asking, while the same command without `$r = ` asked. The command on the right of an assignment (`$x = …`, `[string]$x = …`, `$x += …`, `$a, $b = …`, `$x=…`, a chain like `$a = $b = …`) is now judged exactly as if it stood alone, every stage of its pipe included, also inside `pwsh -c '…'`. A path kept in a variable still asks as before, at every level for Agent Rishi's own files, the agent CLIs' logins and agents' allow-lists (`$t = '…\install-token'; Get-Content $t`, `$p = '.cursor\cli.json'; Set-Content $p …`). Plain values (`$a = 1`, `$s = "text"`, `$h = @{ a = 1 }`) and reads in the worktree (`$items = Get-ChildItem .\src`) still run freely, and `$names = (Get-ChildItem env:).Name` no longer asks, like the same command alone.
- **PowerShell downloads saved outside the worktree, and files reached through `${C:\path}`, now ask at Auto.** `Invoke-WebRequest https://… -OutFile C:\Windows\Temp\x.exe` ran without asking, as did `iwr`, `irm`, `Invoke-RestMethod` and the `curl` and `wget` aliases with `-OutFile`, and `Start-BitsTransfer` with `-Destination`. Agent Rishi now judges where the download is saved, as it judges `Set-Content`. PowerShell's variable syntax for a file also slipped past every check: `${C:\Users\me\.ssh\id_ed25519}` reads the file and `${C:\Users\me\.bashrc} = '…'` writes it. Reading a secrets file this way now asks, as `Get-Content` does, and so does writing outside the worktree. `Get-Content ${env:USERPROFILE}\.aws\credentials` and `Set-Content ${env:USERPROFILE}\…` ran freely too, because the braced `${env:…}` form wasn't read as a path; they now ask like `$env:USERPROFILE`. Downloads into the worktree or temp (`-OutFile .\vendor\x.zip`, `-OutFile $env:TEMP\x.zip`), `${env:PATH}` and other variables still run freely.
- **Auto asks after a pop that may not go back.** `popd -n`, `popd` or `Pop-Location` with an argument the shell refuses, and a pop after `dirs -c` leave the shell where it is in bash or PowerShell, so a delete after `pushd /etc; popd -n; rm -rf x` now asks. cmd's `popd` ignores its arguments and pops, so what follows is judged both ways. A plain `popd` or `Pop-Location -PassThru` still goes back. A command line that may end up in more folders than can be followed asks at every level.
- **cmd's `start` with a title is read.** `start "" /b reg add …`, `start /b "" reg add …`, `start "title" /wait …` and `start "" /d C:\ cmd /c rd …` ask like the started command run directly, with `/d` naming its folder.
- **A shell started by `Start-Process` is judged by its script.** `Start-Process powershell -ArgumentList '-c','irm … | iex'` (also `pwsh`, `cmd`, `bash`, `sh` and `saps`) asks like `irm … | iex`, and piping a download into `cmd` (`curl … | cmd`, also `cmd /k`) asks like piping it into any other shell.
- **Codex commands run from a folder outside the worktree now ask when they reach files there by a relative path.** Agent Rishi judged the relative paths in a command Codex asked to run as if it ran in the worktree, whatever folder Codex ran it in. So `rm -rf *`, `rm -rf build`, `find . -delete` or `echo x > notes.txt` run in another repository, or in Agent Rishi's own home, ran at Auto and Full without asking, and so did reading `config.json` in Agent Rishi's home and `git push --force-with-lease` in another repository (taken for a push of the session's own branch). They now ask, like the same command with absolute paths.
- **The runner's log no longer shows the command lines of processes it ends.** When it ended processes left running in a worktree, the log line held the first 80 characters of each one's command line, which can carry a token or password. It now names each process by its program's file name and pid only (`node.exe (1234)`), as the "still running there" message already did.
- **Commands an agent runs in a folder outside the worktree now ask, even when they name no path.** Codex, OpenCode and ACP agents (Cursor, Gemini CLI) say which folder a command runs in. Agent Rishi judged a command's paths, but not that folder, so `git clean -fdx`, `git reset --hard`, `git checkout -- .`, `make clean`, `npm install` or `touch x` run in another repository ran at Auto and Full without asking. Such a command now asks, at Full too, unless it only reads (`git log`, `ls`, `git status`, also inside `bash -lc '…'` or `pwsh -Command …`). A folder in Agent Rishi's own home outside the session's own asks at every level, and so does input Codex types into a running terminal, whose shell may have moved since it started, unless it only reads. Commands in the worktree, its extra folders and the temp folder run as before.
- **Commands run in a folder outside the worktree now ask at Auto and Full, for every provider.** `cd /other && git reset --hard`, `git -C /other clean -fdx`, `make -C /other clean`, `npm --prefix /other install` and the like ran without asking, because they name no path to judge. Agent Rishi now follows the folder each command runs in, through `cd`, `pushd`, `Set-Location` and `Push-Location` (also in subshells, `bash -c` and `pwsh -Command`), and through a program's own folder option (`git -C`, `make -C`, `npm --prefix`, `pnpm -C`, `yarn --cwd`, `bun --cwd`, `env -C`, `tar -C`, `GIT_DIR=…`). Anything but a read there asks as a write outside the worktree, so Full asks too, and in Agent Rishi's own home it asks at every level. A `cd` to a folder only known when the command runs (`cd $DIR`, `cd "$(…)"`, `cd -`, `cd ~user`, a wildcard, zsh's `cd old new`) counts as outside until a `cd` to a known folder, and so does a drive switch (`D:`) or a folder option left for `xargs` to fill; `cd "$(git rev-parse --show-toplevel)"` goes to the repository's top folder, and `find … -execdir` runs in the folders it searches. `touch` and `mkdir` (`md`, `New-Item -ItemType Directory`) outside the worktree now ask like other writes. Reads such as `cd ../other && git log` or `git -C ../other status` still run freely, and so does everything in the worktree, temp folders and extra roots. A force push in another repository (`git -C ../other push -f`) now asks as a write outside the worktree, so Full asks for it too.
- **Full weighs every part of a command.** A command with several parts is judged by its most severe part, not its first. At Full, a force push, a secrets-file read or a global install earlier in a command no longer lets a later write or delete outside the worktree run without asking (`git push --force && rm -rf ~/projects`), in any order and in every shell. `sudo` with a write outside the worktree asks at Full too, and so does a Codex patch that mixes files inside and outside it.
- **More commands are read before they run.** The risk classifier now judges the commands inside PowerShell script blocks (`if`, `try`/`catch`, `foreach`, `& { … }`) and shell function bodies, reads escapes the way the shell that runs the command does (a POSIX backslash, PowerShell's backtick, cmd's `^`), and looks through `sudo` with its options, `timeout`, `nice`, `nohup`, `stdbuf`, `ionice`, `time`, `command`, `builtin`, `exec`, `busybox`, `eval` and `Invoke-Expression` to the command they run. A write or delete outside the worktree in any of these asks at Auto and Full; an `eval` or `iex` string that is only known when it runs asks at Auto.
- **More write tools are recognised.** `dd of=`, `ln`, `chmod`, `chown`, `sed -i`, `truncate`, `install` and `unzip -d`, git's `clone`, `init` and `worktree add` destinations and its `--output` files, and paths that a `python -c`, `node -e`, `perl -e`, `ruby -e` or `php -r` one-liner writes or deletes ask when they are outside the worktree. Ordinary one-liners and the same tools inside the worktree or a temp folder run as before.
- **The risk classifier reads more of what a command line runs.** It now judges a script handed to a shell or an interpreter on its input (a pipe, a here-string, a heredoc, also through a subshell or a block), the substitutions in an unquoted heredoc, the commands git, `awk`, `trap`, `alias`, `find -exec` and `xargs` run, the tool a package runner starts (`npx`, `pnpm exec`, `pnpm dlx`, `yarn dlx`, `bunx`, `uv run`), and what `flock`, `chroot`, `strace`, `watch`, `su -c`, `taskset` and `unbuffer` wrap. In PowerShell it reads .NET file calls, script blocks made from a string and encoded commands. A write or delete outside the worktree in any of these asks at Auto and Full; a script that is only known when it runs asks at Auto.
- **Paths are read the way the shell reads them.** A one-letter root path such as `/c` is a path for every tool but cmd's own commands, a variable set earlier on the command line is filled in where it is used, and a write or delete target that is still a variable, a parameter or a substitution asks at Auto and Full. In PowerShell, `copy` and `move` read `/x` as a path too. An escaped program name is read as the program it names. Reads don't ask.
- **More write tools are recognised.** `curl -o`, `wget -O`, `sort -o`, `patch -o`, `gzip`, `gunzip` and `xz`, `mkfifo`, `sqlite3`, `git config --file`, `git submodule add` and `git checkout-index --prefix` ask when they write outside the worktree. The same tools inside the worktree or a temp folder run as before.
- **Trusted proxy rules.** A request that names a trusted origin's host counts as coming from another device even from this computer, so it can't use the install token or reach `/mcp`. A request a proxy forwards for any other host (a client can put `127.0.0.1` in `Host`) is refused, so nothing through a proxy passes as this computer. Sign-in throttling through it keys on the forwarded address with one shared limit, and Tailscale identity headers are never trusted.

### Security

- **More ways of dumping the environment now ask for approval at Auto.** Until now only `printenv` and `Get-ChildItem env:` asked. Bare `env`, `export -p` and `declare -x`, `set` (in POSIX shells, and cmd's `set` and `set NAME`, which lists every variable starting with NAME), `[Environment]::GetEnvironmentVariables()`, `node -e`, `bun -e`, `deno eval` and `python -c` code that prints `process.env` or `os.environ` whole, and reading `/proc/self/environ` (any process's `environ`, from the shell or the Read tool) ask too. Running a command through `env` (`env -u NAME pnpm test`), setting variables (`export NAME=…`, cmd's `set NAME=…`), shell options (`set -euo pipefail`), single variables (`process.env.NODE_ENV`, `os.environ.get("HOME")`), names-only listings (`compgen -e`, `env -0 | cut -z -d= -f1`, `Object.keys(process.env)`) and searches for `process.env` still run freely.
- **Names-only environment listings can no longer be steered into printing values at Auto.** Three kinds of listing looked names-only but could print values, so they now ask for approval. The first cuts lines at `=` (`printenv | cut -d= -f1`, `sed 's/=.*//'`, `awk -F= '{print $1}'`, cmd's `for /f "delims==" %i in ('set') do @echo %i`): it passes on the other lines of a value that spans several, such as a private key. The second runs a `Where-Object` or `Sort-Object` script block that does more than compare, such as `{ Write-Host $_ }`, which prints every entry. The third keeps the entries in a variable (`-OutVariable v`) for a later `$v` to print. Exact listings still run freely: `compgen -e`, NUL-separated `printenv -0 | cut -z -d= -f1` (or `sed -z`), `Get-ChildItem env: -Name`, and filters that only compare names, such as `Where-Object { $_.Name -like 'AGENT_RISHI*' }`.
- **A delete that takes its paths from a pipe now asks at Auto when they're outside the worktree.** `Get-ChildItem C:\Users | Remove-Item -Recurse` used to run without asking, because `Remove-Item` named no path of its own. Agent Rishi now checks the paths the command at the head of the pipeline names, or the folder it lists when it names none (`Get-ChildItem -Recurse`, `find -name x`, after a `cd`). The same applies to `… | ForEach-Object { Remove-Item $_ }` and `… | xargs rm`, and the paths `xargs rm` and such a `ForEach-Object` block name themselves are checked too. A path given as `-Path:x` or in a PowerShell list (`dist,C:\Users`) now counts for a plain `Remove-Item` as well. Piped deletes in the worktree, temp, extra folders and environment variables (`Get-ChildItem env: | Remove-Item`) still run freely.
- **Commands run by a cmd `for` loop now ask for approval at Auto like the same commands on their own.** The command a `for /f` loop reads, such as `for /f "tokens=*" %i in ('set AWS') do @echo %i`, ran freely, because the quoted command was read as a single word. This loop prints every variable whose name starts with `AWS`, values included. The command is now judged on its own, also when it's written in double quotes (`('"set AWS"')`), which `cmd /c` drops before running it. So are the files `for /f` reads (`for /f %i in (.env) do @echo %i`) and the command after `do` (`for %i in (1) do set AWS`). Reading Agent Rishi's own credentials this way asks at every level. cmd's `@` before a command (`@set AWS`) no longer hides it either. Loops that print no values, such as `for /f %i in ('git rev-parse HEAD') do @echo %i`, still run freely.
- **`find` and `fd` deletes outside the worktree, and registry deletes, now ask at Auto.** `find ~/projects -name '*.log' -delete`, `find ~/Documents -type f -exec rm {} \;` (also `-exec rm -rf {} +`, `-execdir`, `-ok`) and `fd . ~/old -x rm` used to run without asking. Agent Rishi now treats them like `find ~/projects | xargs rm`: they delete in the folders they search, or in the current folder when they name none. `Remove-Item HKCU:\Software\Foo -Recurse` also ran freely, because the registry key looked like a relative path in the worktree. Deleting registry keys and values and certificates (`HKLM:\…`, `Registry::…`, `Cert:\…`, `Remove-ItemProperty`, `reg delete`) now always asks. Deletes in the worktree and temp, and of the shell's own `Env:`, `Variable:`, `Function:` and `Alias:` drives, still run freely.

### Changed

- **Dictated text appears while you speak.** With Local (Whisper), ElevenLabs or OpenAI, dictation used to record everything and show the text only after you stopped. Now the recording is split on short pauses, and each phrase is transcribed as soon as it ends, so text arrives phrase by phrase. Each piece of audio is still transcribed once, so cloud dictation costs no more. Stopping transcribes the last phrase, and the phrases always land in the order you spoke them.
- **The composer shows what dictation hears.** While you dictate, a line under your text shows a live microphone level and "Listening…" before any text arrives, "Transcribing…" while a phrase is on its way, and words still in progress in muted italics. With the browser engine, its interim words show there too and move into your message once they're final. If dictation fails partway, the text already transcribed stays in your message.
- **Fork, Hand off and Review say up front when a project folder isn't a git repository.** In such a project the session's ⋯ menu, the command palette, the GitHub panel and the model picker's other providers now list these actions as disabled, with the reason "The project folder isn't a git repository". Before, they either showed a generic "Only sessions on a git branch…" reason or stayed enabled and failed with an error when used. **Fork from here** is no longer shown on such a session's turns.
- **A dark factory's review follow-ups wait for the scout instead of becoming issues at once.** When a pull request merges in a dark factory with scheduled scout rounds on, its low and medium follow-ups are held as findings for the scout. In its next round the scout weighs them with its area reviewers' findings and files at most **Issues per round** in total, so follow-ups no longer add builds, reviews and pull requests faster than the scout's limit. It may file from them alone, without planning review areas.
  - A `high`-severity follow-up, or one in the `security` area, is still filed at once and doesn't count toward the round's limit.
  - The held list stays short. A follow-up whose title matches an open issue is linked to it, and one matching a follow-up already held isn't held twice. At most 50 are kept, with the oldest low-severity ones dropped first, and one the scout hasn't filed after 14 days is dropped.
  - The scout's card on the factory panel and in the Factory view shows **N held follow-ups**. Its list shows each with its source pull request and severity, plus **File now** and **Dismiss**. The item page marks a follow-up "held for the scout", or why it left the list, and the daily digest says how many were held, filed, dropped and dismissed.
  - The software factory is unchanged: follow-ups stay on the item page with **File issue**. A dark factory with scheduled rounds off (**Review when fewer than** 0) files every follow-up at once, as before. Issues already filed for follow-ups are left alone.
  - API: `POST /api/projects/:id/factory/items/:itemId/follow-ups/dismiss` (`{ index }`) dismisses a held follow-up, and `follow-ups/file` is **File now**. The factory status lists them in `scout.heldFollowUps`, and the digest counts them in `followUps`.
- **The factory merges pull requests seconds apart instead of one CI run apart.** With auto-merge on, every pull request that passed its checks now merges on the same check of the loop, oldest approved first. Before, the merge queue took one step per check and re-tested most pull requests against the default branch first, so five green pull requests could take half an hour.
  - **A pull request that is behind the default branch merges on its own green CI**, the way it would if you merged it on GitHub yourself. GitHub reports conflicts, and CI on the default branch is still watched after every merge: a merge that breaks it is reverted.
  - **It is re-tested first only for a clash Git can't see:** the pull request and the commits it is missing both changed dependency files (lockfiles, `package.json`), or both changed database migrations. A shared barrel (`packages/*/src/index.*`), a CI workflow, build config or a file both sides touched no longer forces a re-test.
  - **A waiting pull request no longer blocks the queue.** One whose CI is still running, or that waits for a re-review, is passed over, and the ready ones behind it merge.
  - **Re-tests run side by side**, and the other pull requests keep merging meanwhile. A pull request that changes the same kind of files as one being re-tested waits for it ("merges after #12") instead of being re-tested twice.
  - The **Strict** merge policy, a red default branch and branch protection that requires up-to-date branches still re-test every pull request, one at a time.
  - A pull request GitHub refuses to merge for a reason other than being behind now counts toward the three refusals that take it out of the queue, also when other pull requests merged in between.

### Fixed

- **New sessions in a folder that isn't a git repository run on the first message.** They used to ask for a worktree, so the first message always failed with "… is not a git repository". The next message then ran in the project folder without saying so. Now such a project's sessions run in the project folder from the start. The New session view shows **Project folder** and lists **New worktree** disabled with the reason. A worktree asked for there (by the API, a fork, a handoff, a review or the factory) is refused when the session is created, with `not_a_repo`.
- **A session whose worktree couldn't be made no longer runs in the project folder instead.** The next message prepares the worktree it asked for again, and says why when it still can't be made.
- **Sessions without a worktree have the right panel again.** A session that runs in place, in a project folder that isn't a git repository or started in the project folder, now has the right-panel toggle and `Ctrl \`. Subagents, the browser, files, the terminal and details all work in the session's folder, and a subagent card's **Open** shows the subagent beside the transcript. In a folder without git, the Diff tab says "Not a git repository" instead of waiting for checkpoints that never come, and Details shows the folder the session runs in.
  - Runner: a git command in a folder outside any repository fails with `not_a_repo` instead of `git_failed`, and the server answers it with `409 not_a_repo`.
- **Failed factory sessions no longer pile up in the sidebar.** When a factory reviewer fails and the factory starts a fresh one, for example on another provider after a CLI that's too old, an expired sign-in or a usage limit, it archives the failed reviewer as soon as the replacement starts. When an item finishes, any of its sessions that failed are archived with the rest, wherever they worked. Archiving works as usual: the worktree is removed, unless it has uncommitted changes.
  - A failed session that is still the item's current builder or reviewer stays visible until someone retries or the factory recovers the item, because it needs attention. A reviewer that failed also stays until its replacement has started, while the item's note says why.
  - On the first start after the update, the factory archives the failed sessions that earlier versions left behind once their item had finished or a later session had replaced them. It does this once, so a session you restore afterwards stays.
  - The factory item page lists the item's **Earlier sessions** (replaced reviewers, earlier attempts), with their status and whether they're archived. Archived sessions are still one click away.
- **"Keep going until checks pass" stops at its round limit for good.** The round count used to start again after any turn the user's message didn't start: Compact now, or the automatic "continue" after a usage limit, a failure or a restart. A session that kept hitting usage limits could loop unattended with no end. The count now lives on the session. Only a new message (from you, a PM or the factory) or switching the loop off and on starts it again. Turns Agent Rishi starts itself never do. Once the checks still fail after the last round, they don't run again until one of those happens.
- **Compact now waits for running checks.** While the project's checks run after a turn, **Compact now** is disabled with the reason. The API refuses it with `checks_running`, so the run and its results are kept.
- **A check that leaves a process in the background finishes.** A check that started a server or watcher in the background never ended, and every later check for that session was refused until the runner restarted. A check now ends when its own process exits, and whatever it left running is killed with it. Stop and the timeout always end a check, even once its shell has exited. A check that an Agent Rishi restart cut off is cancelled on the runner when the runner reconnects.
- **A failed compaction no longer restarts finished work.** When "Compact now", or the factory's compaction between scout rounds, hit a usage limit or the provider process exited, automatic retry sent "continue where you left off" and the agent ran its last, already finished task again. Compaction turns are now marked as such: a failed one leaves the session idle with its error ("Compaction failed · …") and nothing retries it, so compacting again is up to you.
- **Compactions no longer wake the PM.** A finished compaction used to send the PM, and the orchestrator, a "Finished" notice and wake it, several times per scout round. Compaction turns now send no notice; normal turns notify as before.
- **Steering during a compaction is queued, not a 502.** A message sent to steer a session that is compacting (from the composer or the PM) now waits in the queue and goes once the compaction ends. A direct steer is refused with a clear message instead of a raw 502 error (Codex).
- **Agents no longer stop for approval to list the names of their environment variables.** At Auto, a listing that shows only names runs without asking. In PowerShell that covers `Get-ChildItem env: | … | Select-Object -ExpandProperty Name`, `ForEach-Object { $_.Name }`, `(Get-ChildItem env:).Name` and `Get-ChildItem env: -Name`; in POSIX shells, `printenv | cut -d= -f1`, `sed 's/=.*//'` and `awk -F= '{print $1}'`; the same commands from cmd or `bash -c` / `pwsh -Command` run too. Clearing variables in the agent's own shell also runs (`Remove-Item Env:…`, `… | ForEach-Object { Remove-Item "Env:$($_.Name)" }`, `unset`, `env -u`). In a dark factory these checks used to stall builders and reviewers until someone approved them. Anything that prints values still asks, as before: `Get-ChildItem env:` on its own, `printenv`, a filter or sort on values, or names passed on to look their values up (`… | ForEach-Object { $_.Value }`, `… | xargs printenv`).
- **Factory briefs no longer tell agents to unset Agent Rishi's internal variables before running tests.** Agent sessions haven't inherited Agent Rishi's `AGENT_RISHI_*` variables since 0.7.1, so the advice is out of date. A lesson that still gives it is left out of every brief and the Factory panel, and a review that suggests it again isn't kept.
- **Diffs and push for a session in a folder that isn't a git repository say why they can't answer.** Agent Rishi keeps no checkpoints there. The session's diff used to answer "This session has no checkpoints yet" (there never will be), and a push "Cannot push a detached HEAD". Both now answer `409 not_a_repo`, as its uncommitted diff, restore, git status and commit already did.
- **Dictation with OpenAI, ElevenLabs or local Whisper no longer sends the hum of a noisy room as speech when it starts.** Pause detection used to learn the room's noise level from zero, which took about five seconds. Until then, a fan or air conditioner louder than the quietest level counted as speech, so the room went to the engine as one long clip (and Whisper tends to invent text for it), and your first phrase came back late with that clip. Now the first fifth of a second sets the noise level. If you are already talking when the microphone opens, you are still heard, and the moment of silence some microphones send while they start doesn't count.
- **Dictation in Chinese, Japanese, Thai and other languages written without spaces no longer adds spaces where you paused.** With Local (Whisper), ElevenLabs or OpenAI, each phrase was joined to the one before with a space, and dictated text got a space after text you had typed. Now the space is left out when the text on both sides is in such a language (Chinese, Japanese, Thai, Lao, Khmer or Burmese). Where it meets a word in a language written with spaces, such as English, the space stays.
- **Push-to-talk on the space bar works.** A push-to-talk shortcut recorded with Space (for example Ctrl+Shift+Space in Settings > Voice) never started dictation, because the saved shortcut didn't match the key press. Holding it now starts dictation, and releasing Space stops it.
- **A factory reviewer that was stopped and replaced is now archived.** When a reviewer session stops (for example, someone stops it) and the factory starts a fresh reviewer, the stopped one now becomes one of the item's earlier sessions and is archived like any other replaced reviewer. A reviewer that worked in a worktree of its own (a clean worktree on the pull request's head) used to stay in the sidebar after the item finished, and so did its worktree.

- **The factory's size check leaves out drizzle-kit's migration snapshots.** A pull request that adds a database migration no longer counts the thousands of lines of `snapshot.json` that `drizzle-kit generate` writes beside it (`<timestamp>_<name>/snapshot.json`, or `meta/0003_snapshot.json` in older drizzle-kit versions), so one migration can't push a small change over **Largest change**. The migration's SQL still counts.

### Fixed

- **The dark factory's scout and its area reviewers no longer time out reporting when the factory is busy.** Planning a round waited inside the scout's tool call for each area reviewer to start or wake. Under load that took longer than the call could wait, the round sat in planning with no reviewers until its three-hour timeout, and the project's loop stalled behind it. Reporting findings and filing issues also waited behind the factory's loop. Now all three are recorded and answered at once, never behind the loop, and asking again after a timeout returns the same plan or the issue already filed, or says the findings were already reported. Area reviewers start as agents free up. If no agent frees up within 15 minutes, the round closes with a note in the scout's status and the next one is scheduled. A round already stuck in planning closes the same way after a restart.
- **Long sessions open fast and stay light.** Opening a session used to download its whole transcript, so long-lived PM, orchestrator and scout sessions sent megabytes on every open and grew with every turn. A transcript now opens at its latest 20 turns, and scrolling to the top (or the "N earlier turns" button there) loads the 20 before them, keeping your place. A search hit or link to an older message loads back to that message. The Factory view's quick PM chat fetches only the three turns it shows, and read-aloud only the latest few.
  - API: `GET /api/sessions/:id/snapshot` takes `turns` (the latest N root-thread turns, with their items and the subagent threads they started), `before` (the page before a turn) and `item` (reach back to an item's turn). `SessionSnapshot.earlierTurns` counts the root turns left out. Without `turns` it still returns the whole session.
- **The factory no longer merges commits pushed after the review approved.** An approval now covers the one head commit the reviewer was asked to review. When new commits land on the pull request afterwards (from the builder, a conflict resolution or anyone else), the review check goes back to waiting. The reviewer then reviews only what changed since the approved commit, and the item says why: "New commits since the approval (abc1234 → def5678): re-review running". The merge queue checks the approval again right before it merges, so a head that moves at the last moment never merges unreviewed. Merging the default branch in (Update branch), or a rebase that only brings its commits in, leaves the pull request's own changes as they were and keeps the approval, so the merge queue isn't slowed.
- **The app no longer loads every session ever on start, and live updates stay fast as sessions pile up.** The app snapshot carried every archived session, so a busy factory made each reload slower and each session update more expensive, day after day. It now carries the sessions that aren't archived plus the ones archived in the last 7 days (at most 100), and the server counts each project's archived sessions for the sidebar's "N archived" row. A project's Archived list loads 50 at a time with **Load more**. Older archived sessions still open from a link, a transcript search hit or a factory item: they are fetched when needed.
- **Number fields can be cleared and typed over.** Deleting the last digit of a number setting left a "0" behind, so typing 2 gave "02", and on a phone the first digit was hard to change. Every number field in Agent Rishi (factory limits, merge checks, the scout, budgets, model prices, automation guards, hook timeouts and settings) now works the same way:
  - While you type, the field keeps your text, so it can be empty and a new number replaces the old one. Focusing it selects its number, so you can type straight over it.
  - When you leave the field or press Enter, it tidies up: "05" becomes 5, a number above or below what the setting takes is set to the highest or lowest allowed with a short note ("The most is 8."), and an empty or unreadable entry goes back to the number from before your edit, with a note. A field that can be empty, such as "No limit", saves as empty.
  - Phones show a number keyboard, and the decimal keyboard where a fraction makes sense (budgets and prices in USD), which take a dot or a comma.
- **A session can look at its own screenshots again without asking.** Since Agent Rishi's home became off limits, reading the `File:` path that `browser_screenshot` prints asked at every level, Full included, so factory builders and reviewers that checked their own screenshot stalled on an approval. Reading the session's own artifacts folder (`artifacts/<session id>` in Agent Rishi's home) now runs freely, as in its own worktree. Other sessions' artifacts, the artifacts folder itself, wildcards and searches that reach past the session's own folder, and writing or deleting there still ask.
- **An approval with a non-blocking note no longer loops through revise rounds.** A reviewer that approved with a note in its security concerns failed the security check, so the builder was asked to fix what the reviewer had said could wait, and the same commit was reviewed again until the revise rounds ran out. Security concerns now always block the merge, and `factory_submit_review` refuses an `approve` that lists one: the reviewer asks for changes, or moves the item to the new **follow-ups**.
  - **Follow-ups** are the review's non-blocking findings (up to 5, each a title with an optional severity and area). They never fail a merge check or start a revise round.
  - Once the pull request merges, the dark factory files each follow-up as an issue, labelled `agent-rishi-factory` and `agent-rishi-follow-up` and linked to the pull request, and takes it on like any other issue. In the software factory they're listed on the item page with **File issue**. A follow-up whose title matches an open issue is linked to that issue instead, and none is filed twice.
  - API: `ReviewVerdict.followUps`, `FactoryItem.followUps` (each with the `issue` that tracks it) and `POST /api/projects/:id/factory/items/:itemId/follow-ups/file` with `{ index }`.
- **The factory stops retrying a provider whose login expired every 30 minutes.** When a factory session fails because its provider isn't signed in (such as OpenCode answering `Request failed: 401` for an expired OpenAI login), new factory work now skips that provider until its login changes, instead of trying it again every half hour and failing each time:
  - The provider is used again once detection sees a different login (signed out and in again, another account, a new expiry), when you press **Check now** on the factory panel or **Retry** a failed run on it, or after 6 hours in case the change can't be seen.
  - The back-off survives a restart, so restarting Agent Rishi no longer triggers a fresh failure.
  - You get one inbox item per provider, such as "OpenCode isn't signed in (openai/gpt-5.5): run `opencode auth login`", instead of a "Run failed" item for every pull request. Later failures update it, and it closes by itself once a factory session on that provider works again.
  - Usage limits and failed starts still back off for a set time.
- **A red default branch no longer stays red because the factory's own revert can't merge.** The revert the factory opens when CI on the default branch fails after one of its merges used to fail the test-results and screenshot checks at once, leaving the loop paused with nobody to merge it. A revert now has its own merge rules: its own CI run is its test evidence, it needs no screenshots, its size isn't counted, and when it is exactly the inverse of the merge (checked by comparing trees) an automated check stands in for the agent review (a revert an agent had to resolve conflicts for still gets the normal review). It merges first once its CI is green, whatever the daily merge limit. When CI on the default branch is green again, the loop resumes by itself and the reverted work goes back to its builder as a revise round with the checks that failed. A revert that can't merge (CI red on it too, conflicts nobody resolved) raises one inbox item, "main is red and the revert can't merge: …", and the loop stays paused for you.
- **The factory no longer takes an open issue in twice once a project has more than 500 work items.** Intake only checked the newest 500 items, so an open issue whose item had dropped out of them looked new and got a second work item. That happened to ignored issues from untrusted authors, failed or rejected items whose issue stayed open, and items that waited a long time in the backlog. Intake, recovery, closing replaced pull requests and the loop's other steps now see every item. Only the Factory view still lists the newest 500.
- **Factory ticks read the work items once.** Each tick used to re-read and re-parse the item list about 25 times, and every scout and PM factory call queued behind it. The tick's steps now share one read.
- **A pull request opened before the spec was approved no longer skips the approval.** With "Approve specs before building" on, a PR found on the builder's branch while the spec waits for you or is being revised (one the agent opened with `gh pr create`, or one opened by hand) is no longer taken into review. The item stays at its approval step, its page says "A pull request was opened before the spec was approved", and the factory comments once on the PR that it waits for the approval. After you approve the spec, that PR is reviewed as usual. If the work stops before the spec is approved, the factory closes the PR with a comment.
- **The web UI opens faster, especially on a phone.** A first load used to download the whole app (4.2 MB) before any page could render. It now downloads about half of that (2.1 MB, 660 kB compressed): each page, the terminal, diffs, the code editor, the usage charts and the Factory view load the first time you open them. A tab left open across an update reloads when it opens a page whose code has changed, and a panel offers a Reload button instead of staying blank.
- **Older archived sessions keep their features in the inbox, the Diff panel and the Factory view.** Since the snapshot carries only recently archived sessions, three views lost features for older ones without an error. They now look those sessions up from the server. A failed run's Retry is off again while its provider can't run, and it offers "Continue on another provider", also from the error toast. The Diff panel's "Compare with…" lists a fork's, hand-off's or review's archived source. The Factory view's cards and pixel-mode agents show their provider and last activity again. Each view fetches all the sessions it's missing in one request, and only once.
- **Approved specs no longer stall the software factory, and Stop now no longer builds a spec you haven't approved.** With "Approve specs before building" on:
  - Specs you approved while **PRs open at most** was reached no longer count against each other. Before, once more of them waited than the limit allowed, none was ever built and no new work started. They are now built in the order you approved them, as many at a time as there is room for.
  - **Stop now**, or a drain that runs out of time, leaves a spec that waits for you waiting. Its agent is stopped, its inbox item stays open, and nothing is built until you approve it. Before, the spec went back to the queue, its inbox item closed, and a new agent was told to build it.
  - Approving a spec, or asking for changes, from a page or inbox card opened before the agent revised the spec is refused with "The spec changed since it was shown", and the page shows the new spec. API: the decision takes an optional `version`, the spec's `requestedAt`. A decision on any other version answers 409 `spec_changed`.
- **A revert whose CI on the default branch never says green no longer leaves the factory paused silently.** If CI doesn't report on the revert's merge commit in time (no run after 10 minutes, or still running at the watch limit), the factory checks once more. If there's still nothing, the regression's inbox item becomes "main is red or unverified after revert #N: CI didn't report", and a late green run still resumes the loop. If CI on the revert's merge commit is red, that same inbox item says main is still red after the revert; before, you got a second, generic "loop paused" item. When you resume the loop, the reverted work goes back to its builder once, as it would after a green run.
- **Spec approval and spot-checks are easier to read and act on.** On a factory item's page, a spec waiting for approval now comes before **Approve spec** and **Request changes**: you read the analysis and the acceptance criteria first, then decide. The spec renders as formatted Markdown, in full, where it used to show raw syntax in a small scrolling box. The analysis outcome is in words ("Build it", "Out of scope", "Not reproduced"), where it used to show the raw value.
  - The inbox's **Open spot-checks** opens the project page scrolled to the Spot-checks list, open, with the first merge waiting for a look in view. It used to open at the top of the page, far above the list.
  - The PR view opened from a spot-check has **Looks good** and **Found a problem** in its footer, so you record what you found where you read the change. The dialog closes once it's recorded.
- **The inbox no longer says "You're all caught up" while it is still loading.** Opening `/inbox` directly (a notification's **Open**, a desktop deep link, a bookmark, a slow connection or a server restart) showed "0 waiting on you", zero on every filter and **You're all caught up** until the app had loaded, then the waiting items a moment later. It now shows placeholder rows and no counts until the inbox has loaded. The empty state appears only once Agent Rishi knows nothing is waiting, merge conflicts included. If conflicts can't be loaded, the page says so instead of claiming you're caught up. Two other views had the same problem while loading: Settings > General > Agent environment said "Add a project to choose this per project", and Usage > Budgets labelled per-project budgets "Deleted project" and said "No budgets yet". Both now wait for their data before saying either.

### Security

- **A session's Markdown export hides secrets.** **Copy as Markdown** and **Download as Markdown** replace anything that looks like a secret with `[redacted]`, and the file's summary says how many values were hidden. This covers GitHub, OpenAI, Anthropic, AWS, Slack and other token formats, JSON Web Tokens, bearer tokens, passwords in URLs, private keys, values of secret-named settings such as `GITHUB_TOKEN=…` or `--password …`, and your Agent Rishi install token. Both menu items now say "Secrets redacted". A literal `</details>` in a message can no longer close a subagent's folded block early.
- **Claude Code sessions no longer show their Agent Rishi MCP token on the command line.** Before, the session's bearer token was in the `claude` process's command line, where any local process (and, on Linux and macOS, other users of the computer) could read it and call Agent Rishi as that session, a PM or the orchestrator included. Claude Code now reads its MCP servers from a private file in its own owner-only folder (`~/.agent-rishi/runner/mcp`), deleted when the session ends. Agents ask at every level before reading another session's file, and `attach_evidence` and `share_to_chat` refuse them. No provider puts the token on a command line any more.
- **Remote images in Markdown wait for a click.** An image from another host in an agent or PM reply, a GitHub issue or pull request body, a comment, an inbox item or release notes now shows a placeholder naming its host. **Load image** fetches it through Agent Rishi's server, which contacts only public internet addresses and passes on only images. Before, the image loaded as soon as the reply was shown, so a prompt-injected agent could send data to any host just by being read. Inline images and Agent Rishi's own stored files still show at once.
- **Links in Markdown show where they go.** Clicking one opens a dialog with its real address, **Copy link** and **Open link**; `javascript:` and `data:` links stay refused.
- **The UI has a Content-Security-Policy.** The server sends it, and the desktop app sets it on its window: images only from Agent Rishi, `data:` and `blob:`, scripts only from Agent Rishi's own files, connections only to Agent Rishi, and no framing by other sites.
- **The runner's browser no longer opens a debugging port.** The Chromium that holds every session's browser tabs used to listen for DevTools connections on 127.0.0.1, so any program that could reach loopback (another session's agent, another user on the machine, a container) could read every session's pages and cookies, and drive them. Agent Rishi now drives it only over a private pipe, and it opens no TCP port at all. The browser panel and agents work as before.
- **A pull request's file names can't fake diff lines.** The PR view now quotes file names in its diffs the way git does, so a name with a newline, tab, quote or other special character stays a name. If a file's diff still can't be shown, that file says "Couldn't render this file's diff" with a link to GitHub, and the rest of the pull request keeps working.
- **Agents can no longer read Agent Rishi's own home without asking.** Reading, listing, copying or searching anything in `~/.agent-rishi` (or your `AGENT_RISHI_HOME`) now asks at every permission level, Full included, and is refused for Read-only sessions, PMs and the orchestrator. This covers the database with every session's transcript, settings, logs, backups and other sessions' worktrees, not only the install token and runner lock as before. A session's own worktree there works as usual. Every agent, PM and factory brief now also tells agents to get Agent Rishi's state from its MCP tools instead.
- **Load image allows only the exact URL you clicked.** If an image's URL changes after you loaded it, for example when the author of a GitHub issue edits its body, the placeholder comes back and the new image needs its own click. Before, the new URL loaded without one.
- **Only your click fetches a remote image.** **Load image** now asks the server for a single-use id for that URL, valid for a minute, and the image loads from that id. A plain `<img src="/api/remote-image?url=…">` that slipped into Markdown or other HTML, or an unknown, expired or used id, gets 404 and fetches nothing, so Agent Rishi's own address can't be used to get around its Content-Security-Policy.
- **Agents can't change what Agent Rishi runs for them.** A session's checks are fixed when it starts, read from the project's own folder and never from the session's worktree, so an agent that rewrites `checks` doesn't change what runs. An agent's edit to `.agent-rishi/project.json` (edit tools and shell writes alike) now asks at Supervised and Auto, because its setup and check commands run in later sessions once merged.
- **A change to an automation's file no longer keeps it running.** When the `.agent-rishi/automations/` (or `~/.agent-rishi/automations/`) file of an automation that's on changes its schedule, prompt, permissions, agent or guards, Agent Rishi switches it off and your inbox shows the change as a diff: "Automation *name* changed in its file: review and turn it back on". A new name or description keeps it on.
- **Automations never run above the permission level you approved.** Switching one on records its level; scheduled, event and PM-started runs are capped at it, so a file that later asks for Full runs at what you approved until you switch it on again.
- **Agents ask before editing Agent Rishi's automation files and vision.** Writes to `.agent-rishi/automations/` and `.agent-rishi/VISION.md` now ask at Supervised and Auto, like `.agent-rishi/project.json`.
- **The factory never merges changes to `.agent-rishi/` by itself.** Agent Rishi's own folder holds the setup commands every new worktree runs, the checks, the vision and the scheduled automations. It is now always a protected area, built in and whatever the vision says. A pull request that changes anything there is escalated to you, naming the file and why, even with auto-merge on and every other check green. The vision file is protected wherever the project keeps it.
- **Changed setup commands ask before they run.** A new worktree starts from the freshly fetched default branch, so a merged pull request could change its `.agent-rishi/project.json` setup without you pulling anything. Setup that differs from your own checkout's, or from a list you allowed, is now held. The first worktree that finds it asks once in the inbox, listing the commands: **Setup commands changed in #N: run them?** **Run them** allows the list for new worktrees from then on. **Don't run** keeps skipping it without asking again.
- **Factory lessons need a trusted source.** On a public repository anyone can comment on a trusted issue or on the factory's pull request, and those comments reach the builder and the reviewer. A reviewer's lessons are now kept only when nobody outside the project's trusted set commented on the work: write access, the account Agent Rishi uses and the trusted authors are trusted. If GitHub can't be read to check, nothing is kept. A dropped lesson leaves a note on the item. Builder and reviewer briefs also name the people who commented without trust as untrusted input.
- **New lessons are visible before they steer anyone.** Each new lesson is listed once in the daily digest ("New lesson: …, from #12"), and goes into builders' and reviewers' briefs only a day after it was learned. The Lessons panel shows when a waiting lesson starts, so you can forget it first.
- **Factory protected areas ignore case and catch renames.** Protected paths, the vision's protected areas and deploy files now match whatever the case, so a pull request that changes `.AGENT_RISHI/project.json` or `src/Auth/login.ts` goes to a person like one that changes `.agent-rishi/project.json` (on Windows and macOS they are the same file once checked out). A renamed or copied file is checked under its old path as well as its new one, so moving a file out of a protected folder, such as `.agent-rishi/automations/` to `notes/`, or moving a deploy file elsewhere, is escalated too.
- **Moving code into `docs/` no longer skips the factory's review.** The merge checks now count a renamed or copied file under its old path as well as its new one. Before, a pull request in the docs pipeline that moved `apps/server/src/x.ts` to `docs/x.md` looked docs-only and merged without the independent review. Now it is reviewed and needs tests and test results like any other code change. Moving a UI file elsewhere now needs screenshots, and moving code into a vendored or generated folder still counts towards the size limit.
- **The docs pipeline skips the review only for documentation.** A docs work item merged without the independent review whenever its pull request had no code, so changes to `package.json`, lock files, CI workflows or `tsconfig`, or deleted tests, could merge on CI alone with auto-merge on. Now the review is skipped only when every file is prose (`.md`, `.txt`, `.rst`) or a raster image, with renamed files checked under their old path too. Anything else is reviewed like any other change: config, manifests, lock files, workflows, tests, the instructions coding agents load (`CLAUDE.md`, `AGENTS.md`, dot-folders such as `.claude/` or `.github/`) and code.
- **Fast merges re-test every `package.json` and lock file.** A workspace package's `package.json` and any `*.lock` file now always re-test against main before a fast merge, as the root `package.json` already did.
- **MDX and SVG files are reviewed in the docs pipeline.** A docs pull request that changed only `.mdx` or `.svg` files merged without the independent review. MDX runs JSX and imports when a docs site builds, and an SVG can carry scripts, so both are now reviewed like code. Plain prose (`.md`, `.txt`, `.rst`) and raster images (`.png`, `.jpg`, `.gif`, `.webp`, `.ico`) still skip the review.
- **License files always go to a person.** `LICENSE`, `LICENCE`, `UNLICENSE`, `COPYING` and `NOTICE` (bare, as `.md` or `.txt`, or with a variant such as `LICENSE-MIT`) at any depth, and anything in a `LICENSES/` folder, are now always protected, like `.agent-rishi/`. A pull request that changes one is escalated and never merged automatically, whatever the vision lists. Before, `LICENSE.md` and `LICENSE.txt` counted as documentation and could merge without a review.

## [0.7.2] - 2026-11-14

### Added

### Security

- **Evidence checks the name a file is published under.** `attach_evidence` cleans up file names before publishing them, so `-id_rsa`, `notes.p!em`, `credentials.js!on` and `service/account.json` went out as `id_rsa`, `notes.pem`, `credentials.json` and `service-account.json`, past the secrets check. It and `share_to_chat` now also check every name in its published form, and refuse those files with `secret_file`, whether they are attached by path, renamed, or saved as an artifact and attached by id. `attach_evidence` also checks the final names, after `-2` tells repeated names apart. Ordinary files with odd names, `.env.example` and screenshots still attach. See [Security → Files](docs/security.md#files).
- **Agents can no longer switch off Agent Rishi's approvals by writing their own allow-list.** Cursor and Gemini CLI run what their allow-lists permit without asking, so a single `echo '{"permissions":{"allow":["Shell(*)"]}}' > .cursor/cli.json` used to turn approvals off for the session and, once merged, for every later Cursor session in the project. Creating or changing Cursor's `.cursor/cli.json` or `cli-config.json`, or Gemini CLI's `.gemini/settings.json`, `trustedFolders.json`, system settings or policy files, now asks at every permission level, Full included, for every edit and command Agent Rishi judges (Claude Code, OpenCode, Cursor and Gemini CLI calls, and what Codex asks to run outside its sandbox). This covers edit tools and shell writes (redirects, `tee`, `cp`, `mv`, `ln`, `dd of=`, `sed -i`, `git checkout`, PowerShell's `Set-Content`, `Out-File`, `Copy-Item` and inline `node -e` or `python -c` code). - **Gemini CLI starts under an Agent Rishi admin policy.** Its commands always ask, and its edits and MCP tools ask outside plan mode, whatever `tools.allowed`, trusted MCP servers or policy files allow, so Agent Rishi decides each one. Your own Gemini CLI deny rules still apply (`deny` policies in `~/.gemini/policies` or the project's `.gemini/policies`, `tools.exclude`, excluded MCP servers): Agent Rishi repeats your rules above its own, so what they deny stays denied at every level, and what they allow asks. Cursor has no option to ignore a project's allow-list, so it is guarded and reported instead.
- **A warning when a worktree already carries an allow-list.** A Cursor or Gemini CLI session whose worktree has allow rules in `.cursor/cli.json`, `.gemini/settings.json` or `.gemini/policies` names them in its first turn. In the software factory, the warning also goes on the item and into the inbox.
- **Handing off factory or triage work keeps its trust rules.** The brief of a hand-off used to relay the original session's first message, often a factory or triage brief quoting a GitHub issue, as Agent Rishi's own words, and clipped it at 4,000 characters, which could cut off the rule that issue text is data, not instructions. Messages from the factory, an automation, a project manager or the orchestrator are now quoted under who sent them, the rule sits at the top of the brief whenever the work is on an issue or wasn't started by you, and a hand-off or fork of such work records who started it, so it no longer receives PR feedback that its source wouldn't have.

- **The factory looks after every pull request it opened until it merges or closes.** Before, the factory only watched a PR while its item was being verified. PRs of items that failed or were escalated were left alone, and rotted into merge conflicts while the default branch moved on. Now:
  - **Nothing is left to rot.** A PR waiting for you (auto-merge off, a protected area, checks that failed) is kept free of conflicts: its author rebases it, which isn't a revise round. When the author's session is gone, a fresh integrator session does it, briefed with the issue, the PR description and the review history. Merging or closing one on GitHub finishes its item. The factory never merges these itself.
  - **A merge queue.** With auto-merge on, approved PRs merge one at a time, oldest approved first. A PR that is behind the default branch is brought up to date on GitHub first (no agent needed), and merges once CI passes on the new head, so every merge is checked against the latest main. Only the PR next in line is updated, so CI doesn't run on every queued PR at once.
  - **Conflict fixes are re-checked, not re-reviewed.** After an agent resolves conflicts on an approved PR, the reviewer checks only the resolution (`git range-diff` of the old head against the new one) before it merges.
  - **Rebuild instead of fail.** A PR that still conflicts after three requests to rebase is redone from the latest default branch, for the same issue, keeping its analysis or reproduction. The old PR closes with a link to the new one. An item gets one rebuild.
  - **Hiccups don't strand work.** An item that failed for a reason outside its code goes back by itself on the next check after the cause is gone, at most three times. Its open PR is picked up again rather than redone. That covers a builder or reviewer session that died, CI that never started while GitHub Actions are on, and items that failed this way before this release. Such failures no longer count towards pausing the loop.
  - **Only what is truly stuck reaches you.** That is an item that already used its rebuild, a protected area, or CI that can never run (Actions off, no active workflow). It goes to your inbox and to the project manager. In a dark factory it arrives as a recorded decision, so the daily digest lists it.
  - The factory panel has a new **Pull requests** card: the merge queue in order, then every other PR the factory owns, each with its state (checking, waiting for CI, queued, updating, rebasing, rebuilding, superseded, waiting for you, stuck, merged).
- **Transcript search filters and pages.** The results page lists matches newest first, 50 at a time with **Load more**. It filters by project and role and can leave out archived sessions. A match inside a subagent's work opens that subagent's thread beside the session, scrolled to the match. Search stays quick on long histories and keeps the index small. Sessions from before this update are indexed in the background after Agent Rishi starts, so startup isn't delayed: search finds them as indexing progresses, and indexing picks up where it left off if Agent Rishi is closed in the meantime.
- **Choose the factory's reviewer and builder models.** The factory settings have an Agents section: the builder's provider and model, the reviewer's provider and model (Automatic keeps reviewing on a different provider from the builder), and what a review does when its provider is unavailable: review on the builder's provider and model (the default), on any available provider, or wait.

- **The server can drive several runners at once.** Every runner the server talks to is now recorded, with where it runs, its state and when it was last seen, and each session's commands, terminals and browser go to the runner that hosts it. - **A message that arrives during a running turn no longer fails the session.** When two messages reached a session at the same moment (a factory revise or nudge, a PM message, a queued message going out as the turn ended), the second could be sent as a new turn and fail with "A turn is already running", marking the session failed while its agent kept working. Messages now wait in the session's queue behind the turn on its way and go out, in order, when it ends. If the agent turns out to be mid-turn anyway, the message is queued instead of failing.

Both wait for a free agent under **Agents at once**, oldest first.

A phone now shows the list at full width, and tapping a file opens it in the list's place with a **Back** button. The toolbar wraps onto two rows so the whole path and every button fit, with 40 px buttons. Going back keeps unsaved changes, so you can open the same file again and carry on. The tabs scroll sideways instead of wrapping, and skill switches are easier to tap on touch screens. Tablets and desktops keep the list beside the editor.

The message box now tells a screen reader when the list opens and closes and which entry is highlighted. It now follows the summary on the same line, which wraps when it's long. When forking isn't possible yet, pressing it (a tap, a click, Enter or Space) shows why in a toast, for example "Answer what it's waiting on first", and screen readers announce the reason with the button. Before, the reason was only in a tooltip that never appears on touch or keyboard focus, so the press did nothing visible. **Comment** and **Restore file** now sit in each diff file's sticky header next to the file name and the -/+ counts, instead of on top of them. The follow-up chips could then show an older turn's suggestions, and **Fork from here** and the latest turn's footer could appear on the wrong turn. Turns are now listed in the order they started, both when a session loads and as new turns arrive. The automation run status, auto-retry and the agent tools that attach to the current turn get the same order when two turns started at the same moment.

- **Fork from here works on Claude turns from before a context compaction.** In a long Claude session, forking at any turn before the latest compaction failed with "The conversation no longer holds the end of that turn", although the conversation still held it.   - **An approval only covers what the reviewer checked.** Suppose the reviewer was still re-checking one conflict resolution when a newer resolution arrived.   - **A failed rebuild no longer loses its pull request.** When a rebuild ended before its new PR was opened, the original PR vanished from the **Pull requests** card and the factory stopped watching it.   - **Restarting CI respects Agents at once.** When CI never started on a PR, asking its author to push a new commit now waits for a free agent, like every other agent the factory starts.
  - **Protected areas count as stuck.** A PR escalated because it touches a protected area is now marked stuck, like the other cases that need you.
- **Factory reviews no longer fail when a provider is at its usage limit or signed out.** New builders and reviewers only start on a provider that is installed, signed in and not at its usage limit. A review that would have run on such a provider runs on the builder's provider instead, and the item notes why ("Codex is at its usage limit until Tue 06:00"). ### Security

- **Agents can no longer read Agent Rishi's own tokens without asking.** Reading or changing the install token, the runner's lock file or the network access store in `~/.agent-rishi` now asks at every permission level, Full included, and is refused for Read-only sessions, the orchestrator and PMs. The path can be written out or reached through `~`, `$AGENT_RISHI_HOME`, a wildcard or the folder that holds the file, anywhere in a command. **Approve for session** covers these files only for the exact call you approved, in the same directory. Before, an agent at Auto could read the install token and use Agent Rishi's local API to approve its own requests. Codex still runs reads it considers safe, such as `cat`, inside its own sandbox without asking; see [Security](docs/security.md#permissions).
- **The PM can't start work on a stranger's issue unless you asked.** A triage run, a GitHub or factory notice, a wake-up or another agent's message can start a PM turn, and in that turn the PM reads issues anyone can write. In those turns Agent Rishi now refuses `start_session` for an issue whose author isn't trusted (not one of the project's trusted authors, not the account Agent Rishi uses on GitHub, no write access to the repository) and refuses `factory_admit_issue` outright. The PM puts the issue in your inbox instead ("Should I take this on?"). When you ask the PM in your own message, or ask the orchestrator and it passes your request on, the PM can still start work on any issue and let one into the factory.
- **Three more ways around the guard on Agent Rishi's own tokens are closed.** A search with its options packed together (`grep -ne. ~/.agent-rishi/install-token`, `grep -fFILE …`, `rg -e. ~`), a PowerShell list of paths (`Get-Content $env:AGENT_RISHI_HOME\install-token,…`) and an Agent Rishi data folder whose name has `[`, `*` or `?` in it (`Agent Rishi [dev]`) no longer slip past the check. Before, these read the install token, the runner's lock file or the network access store without asking, at any permission level, and a bracketed data folder switched the guard off even for plain reads and writes. They now ask at every level and are refused for Read-only sessions, the orchestrator and PMs.
- **Evidence can no longer publish secrets.** `attach_evidence` now refuses secrets files (`.env`, `.npmrc`, SSH keys, `*.pem`, ...) and Agent Rishi's own credential files, wherever they are and under any name: renamed, reached through a symlink, or saved as an artifact. `share_to_chat` refuses them too, so a secret can't be staged as an artifact and attached by id. Before, an agent could publish its worktree's `.env` to the repository's `agent-rishi/evidence` branch in one tool call, with no approval at any level. `.env.example` and other templates still attach. See [Security → Files](docs/security.md#files).

Before, the tab kept every chunk and redrew all of it, using more memory and CPU the longer a build or test run went on.

- **Fewer false "Pipes a downloaded script straight into a shell" approvals.** Under Auto and Full, commands that pipe a download into a program that only reads it as data, such as `curl … | node -e '…'`, `curl … | python -c '…'` or `curl … | node scripts/x.mjs`, no longer ask. A `|` inside quotes (`sed 's|a|b|'`) no longer counts as a pipe either. Downloads piped into an interpreter that runs them (`curl … | sh`, `curl … | python3`, `irm … | iex`) still ask.
- **Claude sessions on Windows stop asking about files in their own worktree.** Once Claude Code's shell had run a command, it reported its folder in Git Bash form (`/c/Users/you/...`), and Agent Rishi read relative paths from it as if they were somewhere else. `rm -rf dist`, `pnpm test > test.log` or `cp a.ts b.ts` then asked as "outside the worktree", even under Full. They now run freely; files that really are outside the worktree still ask.
- **Fewer temp-folder approvals.** Copying files into the temp folder itself (`cp shot.png /tmp/`, `Copy-Item a.txt $env:TEMP`), using a `$tmp` or `$temp` variable for a folder made with `mktemp`, and `rm -rf *` inside the worktree or a folder in temp no longer ask, under Auto or Full. Copying a secrets file into temp, deleting the temp folder itself and emptying a folder outside the worktree still ask, and `cp file /etc` now asks as it should.
- **Reading global git config and single environment variables no longer asks.** `git config --global user.email`, `git config --global --list` and the like asked as "Changes global git configuration", even under Full; only commands that change it ask now. `printenv PATH` and `Get-ChildItem env:PATH` no longer ask as "Dumps environment variables" under Auto; dumping everything, or a variable whose name looks like a credential, still does.
- **Project managers and read-only sessions can look around more freely.** They were refused ordinary reading commands and wasted turns working around it: `cd x && git log`, `git -C <worktree> log`, `git --no-pager log`, `git stash list`, `sed -n 1,40p file`, `nl`, `gh search` and `gh api` GET requests now run. Anything that writes is still refused, including `sed -i`, `git stash` and `gh api` requests that send data.
- **Far fewer false "secrets file" approvals under Auto.** Searching for `process.env` or `import.meta.env` (with `grep`, `rg`, `Select-String` or Claude's search tool), adding `.env` to `.gitignore`, `test -f .env`, listing `*.pem` files, generating a local dev certificate, and creating an env file in the worktree (`cp .env.example .env`, or Claude writing `.env`) used to ask as secrets access. They now run freely. Reading a secrets file still asks, and so does writing one outside the worktree.
- **Claude's plans and memories no longer ask.** In plan mode Claude writes its plan to `~/.claude/plans`, and it saves memories to the project's auto-memory folder; both are outside the worktree, so each one asked for approval, even under Full. They now count like the temp folder under Auto and Full (honouring your `plansDirectory` and `autoMemoryDirectory` settings). Claude's settings and credentials still ask.
- **Agents can update their own pull request after a rebase.** `git push --force-with-lease` of the session's own branch no longer asks under Auto, and `create_pull_request` now pushes with a lease itself when a plain push is rejected after a rebase, instead of failing. Plain `--force`, force-pushing any other branch (including `main`), and deleting remote branches still ask. `git branch -d`, which refuses to delete unmerged work, no longer asks; `-D` still does.
- **Unattended work no longer waits forever on an approval.** In a Dark factory project, the PM's and the factory's sessions used to stop at an approval until you came back, holding up the whole factory. They now get a denial at once, with guidance to find a way that needs no approval or flag it for you. Sessions started by an automation, a PM or the factory in other modes wait 30 minutes for you, then get the same kind of denial, so a scheduled run finishes instead of blocking the next ones. Nothing is ever approved on your behalf, and sessions you start yourself wait for you as before.
- **Codex stops asking for ordinary work under Auto and Full.** Codex's sandbox keeps `.git` read-only and, under Auto, blocks the network, so it asked for approval for every `git commit`, `pnpm install` or `git push`, and under Full it couldn't commit at all. Agent Rishi now judges what Codex asks with the same rules as Claude: what your permission level allows is approved at once (shown in the transcript as approved by policy), and only risky actions, such as force pushes, writes outside the worktree or reading secrets, reach you. Full now lets Codex step outside its sandbox the same way, asking only for writes outside the worktree.
- **The browser panel keeps working on macOS for very large panels.** Above about 2560×1600, the picture used to be scaled below the page's own size, and on macOS Chrome then stopped sending pictures and reported the wrong page size, which put clicks in the wrong place. The picture now never goes below the page's size.
- **Quitting the desktop app can no longer hang.** If Agent Rishi's background server got stuck while closing, the app waited for it forever and never quit. It now stops the server after a short wait (forcing it if needed), a failed step while quitting no longer leaves the app open, and a server left behind by a crashed app exits by itself.
- **Agents, PMs and the orchestrator stop asking about things they can decide.** They now pick sensible defaults for routine details (approach, naming, scope, provider and model), say what they assumed so you can override it, and keep working; the orchestrator no longer ends replies with a menu of choices. They still ask you before destructive or irreversible steps, spending money or credentials, outward-facing actions such as publishing, releases, deploys or messages to people, and changes to protected areas.
- **Agents commit in their own worktree without asking.** A session started by a PM or an automation opens its pull request when the work is done; in a session you started, the agent opens one when you ask and otherwise offers it as a suggested follow-up. A question at the end of an agent's last message now reaches its PM instead of being cut off.
- **Stop always stops.** A turn whose agent never answered the stop request could stay "Working" forever; it now ends within 10 seconds either way. Messages you sent into a Claude turn that the agent hadn't read yet are dropped with it, instead of starting a new turn right after you pressed Stop, and the transcript says they weren't delivered.
- **No more dead approvals after a crash.** When Agent Rishi's background runner was killed or crashed, approvals and questions from the agent's cut-off turn stayed open in the inbox and could keep the session "Waiting" or "Working" long after it resumed. They're now cancelled before the session continues; questions an agent asked with `ask_user` stay open, since they can still be answered.
- **Agents hear about failed setup commands.** When a worktree setup command from `.agent-rishi/project.json` failed, the session started anyway and the agent ran into confusing errors without knowing why. Its first message now begins with the command that failed, its exit code and the end of its output.
- **You can see when Claude is retrying or compacting.** A Claude session that hit an overloaded or rate-limited API, or was compacting a long conversation, looked stuck while Claude Code recovered by itself. The transcript now shows "The API request failed (overloaded, 529); Claude Code retries in 12s (attempt 2 of 10)", updated as the attempts go up, and "Compacting the conversation…" until it reads "Context compacted" (or says why it failed).
- **New sessions start from the latest code.** In a GitHub project, a session's worktree was branched from your local default branch, even when it was days behind GitHub, so agents worked on old code and opened pull requests with conflicts. Agent Rishi now fetches first and branches from the default branch on GitHub when your local one is only behind; a local default branch with commits of your own is still used as it is, and offline it carries on with the local one. Agent Rishi's git also never opens a Git Credential Manager sign-in window in the background.
- **Archived sessions free their disk space on Windows.** A dev server an agent started through its shell kept running after the agent stopped, kept the worktree in use, and the worktree (often with a large `node_modules`) could never be removed, silently. Agent Rishi now ends what its agents left running in a worktree when the session stops and before the worktree is removed; your own editors and terminals are left alone. A removal that still fails appears in the inbox under **Worktrees not removed**, with **Try again**, and the desktop app now always keeps its server log in `~/.agent-rishi/logs/desktop-server.log`.

## [0.1.0] - first public release

The first public release of Agent Rishi, a local-first harness for coding agents. Install with `agent-rishi`.

### Daily driver

- **Claude Code** through the Claude Agent SDK (using your installed `claude` and its login) and **Codex** through `codex app-server`, behind one normalized event model.
- Agent sessions in their own **git worktrees and branches**, with `.agent-rishi/project.json` setup commands.
- A transcript with grouped tool calls, plans and todos, subagent threads, and approval and question cards answerable inline.
- **Autonomy levels**: Supervised, Auto with risky actions asking (the default) and Full autonomy, mapped onto each provider's native enforcement.
- **Turn checkpoints** in hidden git refs: per-turn and whole-session diffs and file restore.
- **Workbench**: file tree and editor, runner-owned terminals that survive server restarts, and a browser the agents drive and you can take over.
- **Agent configuration** editors for memory files, skills, subagents and MCP servers, written to each provider's native files with a diff preview and a backup.
- **Image generation** for every agent through one `generate_image` tool (Codex, Gemini, OpenAI Images).
- **Voice**: dictation with push-to-talk and read-aloud of final messages.
- **Follow-up prompt chips** when a turn completes.
- First-run setup that detects and reuses existing Claude Code, Codex, GitHub and git setups, and `agent-rishi doctor`.

### Orchestration

- An **orchestrator** across projects and a read-only **project manager** per project, with status digests on every wake and typed notices.
- **Work keys and conflict detection** with wait, skip, join and force.
- One **inbox** for questions, approvals, PRs ready for review, failed runs, triage decisions and conflicts.
- **GitHub** issue, PR, check and review sync through `gh`, PRs that link their issue and session, and screenshots and test output on the `agent-rishi/evidence` branch.
- **Usage and cost reports**: a per-turn ledger, reported versus estimated costs, API-equivalent cost for subscriptions, rate-limit windows, budgets and alerts, and CSV export.

### Automations

- A scheduler with cron, event and manual triggers, guards (overlap policy, concurrency, quiet hours, daily caps, catch-up), runs history and per-project switches. All off by default.
- Built-in templates: security audit, refactor sweep, dependency updates, UI review, test coverage gaps, issue triage and stale PR follow-up. Custom automations as Markdown files.
- Issue triage by the PM, with a "Should I take this on?" inbox decision.

### Autonomy modes (experimental)

- Project modes Manual, Assisted (the default), **Autopilot** and **Dark factory**.
- A `.agent-rishi/VISION.md` editor with protected areas, the factory loop, merge checks with an independent cross-provider review, automatic squash merge and automatic revert, server-enforced limits, a per-project and global kill switch, the factory panel and a daily digest.
